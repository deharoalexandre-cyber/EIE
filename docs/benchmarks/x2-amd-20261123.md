# AMD Ryzen AI Max+ 395 / Radeon 8060S : EIE sur HIP, essai borné

**Statut : EIE compilé et exécuté sur la machine cible avec le backend HIP.**
Gemma, Bonsaï et Nomic ont chacun passé deux requêtes réelles sur la route HTTP
d'EIE, avec placement des couches sur `ROCm0`. Les modèles ont été lancés
séparément, avec des entrées synthétiques et sans données de clientèle. Les mesures
PrismML indépendantes ci-dessous sont des contrôles distincts ; le [reçu EIE
public expurgé](data/x2-windows-hip-20261123.json) et les empreintes des journaux
privés documentent le passage par EIE.

| Moteur de contrôle | PrismML `prism-b10828-a153697`, binaires Windows Vulkan, HIP et CPU |

Les deux temps Bonsaï incluent le traitement du prompt et la réponse, ainsi que les
surcoûts de requête. Ils ne constituent pas un débit de décodage stable : l'échantillon
est trop court et la deuxième requête a été plus lente. Le journal serveur du premier
appel donne séparément 31 tokens de préremplissage en 6,034 s et 42 tokens générés
en 1,818 s ; cela reste un seul appel.

Un second passage HIP avec journalisation détaillée atteste le placement des poids sur
`ROCm0` : Gemma 49/49 couches (6 637,69 MiB de buffer modèle), Bonsaï 65/65
(6 539,67 MiB) et Nomic 13/13 (222,01 MiB). Les projecteurs multimodaux de Gemma
et Bonsaï utilisent également `ROCm0`. Les trois processus ont été testés
séquentiellement, sans mesure de coexistence. Ces journaux établissent l'usage GPU
réel du **serveur PrismML**. L'exécution EIE indépendante est décrite ci-dessous.

## Compilation du serveur EIE sur le X2

Le serveur EIE de la révision `527c4501415ce871b1f66bf2175e50d53fe0d17d`
a été compilé sur la machine cible avec le sous-module PrismML
`a15369706017f177cae8aa40b6b8592259a48806`, HIP SDK 7.2, le clang AMD,
`GGML_HIP=ON`, `GPU_TARGETS=gfx1151` et les outils C++ Visual Studio 2022. La
compilation Ninja s'est terminée avec le code 0. SHA-256 du binaire EIE :
`1c376e0d57a8763dd4d38020f703e7c090456fcc58884d5f9fea8b9aa3ffef6f`.
Le journal de build et le cache CMake sont conservés dans le dossier de
qualification privé ; le cache confirme aussi `EIE_LLAMA_RUNTIME=prism` et
`GGML_BACKEND_DL=ON`.

Le premier lancement du banc EIE a démarré le serveur avec zéro modèle : le
chargeur de backends cherchait les DLL dans le dossier de travail du processus,
alors que le banc lançait EIE depuis la racine du dépôt. Le journal indiquait
`no backends are loaded`. Le banc a été corrigé pour lancer EIE depuis son
dossier de DLL. Le même binaire a ensuite passé les essais ci-dessous, sans
recompilation. Le reçu et le journal de l'échec initial ont été remplacés lors
du second passage ; cette observation n'a donc pas d'empreinte brute conservée.

## Inférence EIE sur la Radeon 8060S

Le banc `scripts/qualify-windows-hip.py` a lancé un **vrai serveur EIE** sur
`127.0.0.1`, un modèle à la fois. Le preset `presets/windows-hip-x2.yaml`
emploie le KV F16 et un contexte de 8 192 tokens. La route
`/v1/chat/completions` a répondu pour Gemma et Bonsaï ; `/v1/embeddings` a
produit des vecteurs pour Nomic. Le contrôle exige deux réponses réussies, un
modèle présent dans `/health`, `ROCm0` dans le journal et toutes les couches
déchargées vers le GPU. Le binaire et les GGUF sont identifiés par SHA-256 dans
le [reçu public](data/x2-windows-hip-20261123.json).

| Modèle, quantification | Démarrage jusqu'à `/health` | Requête 1 | Requête 2 | Placement dans le journal |
|---|---:|---:|---:|---|
| Gemma 4 12B QAT Q4_0 | 2,532 s | 1,532 s ; 38 tokens | 1,468 s ; 40 tokens | `ROCm0`, 49/49 couches, buffer poids 6 637,69 MiB |
| Bonsaï 2 27B PQ2_0 | 2,547 s | 2,313 s ; 50 tokens | 2,156 s ; 50 tokens | `ROCm0`, 65/65 couches, buffer poids 6 539,67 MiB |
| Nomic Embed Text v2 MoE Q6_K | 1,031 s | 0,141 s ; 768 dimensions | 0,016 s ; 768 dimensions | `ROCm0`, 13/13 couches, buffer poids 222,01 MiB |

Les temps de requête sont des temps muraux HTTP incluant le traitement du
prompt ; ils ne mesurent pas isolément le débit de décodage. L'échantillon est
trop court pour une médiane ou une garantie de latence. Ces essais ne testent
pas la coexistence des trois modèles, une charge prolongée, EWS sur ROCm,
ni l'application pilote complète. Le statut de **ROCm sur EIE** correspond ici
à Windows 11, HIP SDK 7.2, `gfx1151`, au runtime PrismML épinglé et à ces trois
GGUF. Linux/ROCm reste une cible de compilation non qualifiée par ce passage.

Les modèles et les exécutables ont été copiés avec vérification SHA-256. Le binaire
PrismML Vulkan testé porte l'empreinte
`4c5f05c11bf999311a670e387e187f624eeb11bafc937c40519a7da1cb609981` ;
le binaire HIP, non fonctionnel au premier passage, porte
`acb605fdc8f65e57cd6c88c29012dbbefc851156aa89eac1439500fa6ab886b0`.
Les journaux complets et reçus bruts restent dans le dossier de qualification privé.

## Étapes suivantes

1. Fait : installer un pilote AMD et un SDK HIP compatibles avec `gfx1151`, vérifier
   `hipInfo` et `ROCm0`, puis obtenir deux réponses de Gemma avec PrismML HIP.
2. Fait : exécuter isolément Gemma, Bonsaï et Nomic avec le binaire HIP et confirmer
   leurs couches sur `ROCm0`. Restent la coexistence des modèles, la dispersion des
   temps et une mesure prolongée de stabilité.
3. Fait : construire **EIE lui-même** sur la machine cible et faire passer ses
   routes de conversation et d'embedding avec les trois GGUF. Restent le
   redémarrage prolongé, la coexistence, les charges représentatives et les
   mesures de stabilité.

La [matrice AMD Windows](https://rocm.docs.amd.com/projects/install-on-windows/en/latest/reference/system-requirements.html)
liste le Ryzen AI Max+ 395 (`gfx1151`) comme pris en charge. La
[documentation AMD de llama.cpp](https://rocm.docs.amd.com/projects/ai-ecosystem/en/latest/inference/llamacpp.html)
demande de vérifier la présence du périphérique, puis un calcul réel ; elle décrit
les bibliothèques HIP qui doivent provenir d'une même installation.
